CHAPTER 01 / COMPANY STRATEGY



Executive thesis and pre-build status
SENTINEL//LADDER is proposed as an adaptive evidence-gated authorization platform for autonomous
AI operations. It sits between claims about the physical world and business actions that could have
financial, safety or operational consequences. Its initial vertical is field-service maintenance: contractor
evidence, manager review, invoice preparation and simulated approval.

The system is not an AI that independently certifies completed repairs. Its strongest claim is that it can
enforce explicit restrictions on what an agent may do with available evidence, preserve a reviewable
decision record and test the rules against known failure cases.


 ONE-SENTENCE PITCH

 SENTINEL//LADDER converts uncertain physical-world observations into bounded agent
 permissions, with human-controlled approval and adversarially tested authorization policies.

Strategic principles
  Vertical-first, horizontal-later — Win one inspectable maintenance workflow before advertising
    general agent-security infrastructure.
  Evidence is bounded — A visible indicator, label or reading cannot alone prove repair success or
    media authenticity.
  No uncontrolled learning — The system may propose security improvements but only reviewed,
    tested policy versions can go live.
  Value is measured — Reduce unsupported approvals without unacceptable false rejections, review
    delays or operating cost.

The initial buying problem
The first target buyer is an operator or software provider managing a high volume of outsourced
inspection and maintenance jobs. SENTINEL is positioned as a control layer that standardizes evidence
requirements and prevents automated actions from advancing ahead of those requirements. The
commercial hypothesis is reduced review rework, lower dispute exposure and safer workflow
automation; these benefits have not yet been measured.

Normal success journey
1.    A work order is opened with an authoritative asset ID, organization, job ID and approved policy.
2.    The server issues a time-limited challenge bound to that case and evidence session.
3.    The contractor captures an authorized image or short clip; intake checks file type, limits, exact
      duplicates and chain-of-custody metadata.
4.    Gemini extracts visible observations. It may return UNKNOWN, missing, or uncertain fields.
5.    The policy engine evaluates exact identifiers, numeric conditions, challenge binding and evidence
      freshness.
6.    The manager reviews a prepared invoice only if the case has sufficient evidence. Consequential
      completion is explicitly approved by a properly authenticated user.
7.    An audit event is recorded; scheduled or sampled security testing evaluates the active policy
      separately.


Failure and exception journey
If an identifier mismatches, a reading is outside policy bounds, the token is stale or evidence is
ambiguous, the case must remain restricted. The contractor receives a clear next action, while the
manager can see the precise reason. Unsafe operating conditions are classified as a safety review state,
not as an upward ladder tier.


 WHY A THIRD ENGINEERING PORTAL MATTERS

 The manager reviews business evidence; engineers review vulnerabilities and change
 permissions. Combining those duties would let a business approval accidentally become a
 security-policy change.

Reference policy invariants
  Model output can never directly invoke payout, send a payment request, publish a new policy or
      assign its own role.
  Every action is checked server-side against the current case state and policy version.
  Expiry or evidence replacement invalidates previously granted approval; stale results cannot be
      reused.
  Missing/malformed numeric data or unrecognized units never silently default to safe values.
  A severe/unsafe observation creates an escalation state, not permission progression.
  A manager cannot approve their own contractor submission where separation of duties is required.

USP in one sentence

 UNIQUE SELLING PROPOSITION

 A runtime evidence-to-permission gateway for physical-world AI workflows, complemented by

Cloud deployment topology
Cloud Run provides stateless APIs and workers; Cloud Storage holds private media; Firestore stores

secrets must use restricted access. Cloud Run autoscaling handles instances, not downstream model
quotas or business correctness. Enterprise concurrency and cost require load testing. [W2]

Atomic approval invariant
An approval must attach to the precise case ID, invoice amount, evidence digest/version, policy version,
and reviewer identity. Any change in one relevant dimension invalidates it. Review and evidence update
transactions must be atomic; a stale request must not restore an obsolete approval.

Identity separation
A visual role switcher is useful for a demo, but it is not access control. The production API must
authenticate contractor, reviewer, engineer and agent credentials independently, with scoped tenants
and job assignments. The Firestore server SDK follows IAM, so authorization must also be enforced in
backend code. [W4]

The approved continuous-hardening loop




Figure 2 | Gemini proposes tests; a reviewer controls policy changes.

16. Generate candidate cases from known failures, policy constraints, and controlled Gemini prompts.
17. Filter for valid schema, scope, deduplication, safe content and independent expected outcome.
18. Run cases against isolated policy versions. Record both false approvals and false rejections.

21. CI tests old and new cases, then authorized personnel release a versioned rule pack.
22. Monitor production decisions and schedule the next review; do not use live customer data for public

CHAPTER 13 / MEDIA ASSURANCE



Verification attacks and defensive layers
Replay: same or edited photograph
Use byte hashes for exact duplicates and calibrated visual similarity only for review. Both methods can
generate false positives or fail when content changes. Require job/session-specific context rather than
trusting image identity as physical proof.


Location: different building or site
EXIF GPS and client browser coordinates are spoofable; a fixed 200-metre rule can reject legitimate
indoor jobs. Use site-authoritative asset ID, reported accuracy, optional location and exception review.
Stronger device attestation is a future integration.


Synthetic image or photo-of-screen
Moiré, reflections and artifact detectors provide investigatory indicators, not a reliable proof of
authenticity. A challenge marker is useful but not conclusive. Controlled capture and trusted sensor
evidence are future higher-assurance features.


Prompt injection embedded in evidence
Schema-constrained JSON is not equivalent to semantic truth. Instructions inside media are untrusted
data and must not influence authority. Model permissions remain read-only; the policy checks known
requirements independently. Cases with uncertainty or conflicts go to review. [W3]


Numerical and temporal edge cases
  Boundary values — Explicit inclusive/exclusive limits and validated units.
  Negative or impossible values — Reject invalid measurements; never silently coerce.

CHAPTER 14 / ENTERPRISE READINESS



Data governance, privacy and auditability
Evidence may expose customer locations, building interiors, personnel and equipment identifiers. A
production version needs defined collection purpose, retention limits, customer-controlled deletion
policies, secure media storage, encryption and tenant-scoped access. Contract and regulatory obligations
depend on customer industry and jurisdiction and require legal review.


Data minimization principles
  Collect only observations necessary for the approval policy.
  Avoid face/biometric identification in the first product; it adds substantial privacy and safety
   obligations.
  Separate raw media from shareable findings and engineering alerts.
  Treat customer-specific policies and test cases as confidential unless explicit rights allow
   aggregation.
  Keep a detailed access trail for evidence reads and policy changes.
  Define incident response and breach-notification ownership before real deployment.


Audit model
Use append-only logical event records with restricted administration, policy/version references and
evidence hashes. Neither SHA-256 nor Firestore alone makes an audit record immutable. A
cryptographic hash authenticates byte identity only if keys, timestamps and storage controls are sound;
a changed event store can still be rewritten by a privileged operator without stronger retention controls.

Glossary
 Term                        Meaning

 Agent                       Software component using models and tools to perform tasks.

 Evidence                    Submitted media or records supporting a claim; may be untrusted.

 Observation                 A model- or sensor-produced statement about visible/measured data.

 Policy Decision Point       Independent component that decides permitted action under explicit rules.

 L0–L3                       Progressive business-action permission levels; not fraud scores.

 Red team                    Controlled effort to identify weaknesses in a system.

 Oracle                      Independent expected outcome used to evaluate a test.

 Regression                  Repeated tests showing previously fixed issues stay fixed.

 False approval              An invalid case incorrectly becomes eligible for action.

 False rejection             A valid case is unnecessarily blocked.

 Tenant                      A customer organization with an isolated data/permission boundary.

 Provenance                  History and origin claims attached to evidence; strength varies by source.



THE NORTH STAR



Build the boundary. Prove the value.
SENTINEL’s opportunity is not that continuous red-teaming or agent authorization has never been done.
It is the possibility of applying these disciplines to a painful physical-world evidence workflow,
separating observation from permission, and validating the results well enough for customers to trust
the system as part of their operations.


 FINAL DIRECTIVE
 Starting with an empty repository, implement one reliable maintenance case from upload to
 bounded action and human review. Run honest tests and a real Gemini evaluation before
 declaring functionality complete. Interview the buyer, then expand only after the evidence is real.
